# RR-016.2 — isolated authentication staging

This is source code and synthetic test infrastructure, not a deployed login system. Do not expose public member signup until provider configuration, privacy/retention notices, abuse protection, rate limits, verified-email/recovery flows and live negative tests are complete.

## Staff
Create a dedicated Cloudflare Worker custom hostname after the domain is confirmed. Before enabling the hostname configure Cloudflare Access for the entire staff host, invitation-only policy and MFA via the staff IdP. Disable workers.dev and preview URLs. Use the actual team issuer (no trailing slash) and exact application AUD. The Worker additionally validates RS256 signature, issuer, audience, expiry, subject and app token type. Access identity headers alone are ignored. A valid token without an active D1 staff record receives 403. The owner must obtain the immutable Access subject through a trusted, verified Access identity record and manually insert the matching issuer/subject with role owner and active status using the authenticated Cloudflare console. No signup or bootstrap HTTP endpoint. Only grant that role to the confirmed owner. Do not paste access JWTs into chat or commit them. If immutable subject cannot be established, stop rather than guess from email. Staff logout uses Access's logout path; test IdP and application session behavior.

## Member
Create a separate Auth0 regular web application, with Universal Login, RS256 ID tokens, database or approved social connections, verified email, password reset and attack protection. Set the exact account-origin callback URL /callback and logout URL /. Enable the authorization code flow and require PKCE where supported. Store MEMBER_CLIENT_SECRET as a Worker secret, not in source or client storage. Set MEMBER_ISSUER to the actual tenant issuer and MEMBER_CLIENT_ID. Member login uses code+PKCE, random state and nonce, one-time D1 attempt consumption, validated ID token, verified email and immutable issuer+subject. The browser only receives secure HttpOnly host-only cookies; server stores hashed opaque session token, expiry at most one hour. Logout deletes the local session and redirects to the provider's OIDC logout. Provider session/revocation and password recovery must be tested in staging. No password, access token, refresh token or ID token stored in D1. Auth0's free tier is a candidate, not a guaranteed cost. Limit staff and member databases to separate staging instances. In production use separate data bindings and least privilege; current migrations contain the common schema in each database and do not automatically synchronise data.

## Deploy only after configuration
Copy the appropriate studio/wrangler.*.example.jsonc to the ignored local studio/wrangler.*.jsonc; replace all placeholders and database IDs, never commit credentials. Apply migrations 0001 and 0002 in each isolated D1 instance. Configure custom domains and Access policies in the Cloudflare dashboard. Deploy with a supported Wrangler version after inspecting configuration. No actual Worker/D1/Access/Auth0 resources or accounts were created here. No public site navigation changed. Use a staging domain and real browser checks first. Test forged/expired tokens, audience and issuer mismatch, disabled staff, unprovisioned Access users, member registration, email verification, callback replay, expiry, logout, password recovery, direct host bypass and no cross-account data exposure. Add edge rate limits and scheduled expiry cleanup before public availability. Existing local CMS stays independent. No editing, billing or premium routes are exposed.
