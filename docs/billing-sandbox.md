# RR-016.5 — Subscription billing sandbox

Disabled by default. No real pricing, provider plans, subscription links, credentials, payment or refunds are created in this change. Only an isolated test member database may be used. Apply migrations 0001–0006. Configure BILLING_MODE=sandbox, the actual Razorpay Test Mode account ID, test key ID, and secrets RAZORPAY_KEY_SECRET and RAZORPAY_WEBHOOK_SECRET through Worker secrets (key ID RAZORPAY_KEY_ID also configured securely). Never use live keys. Explicitly insert one billing_sandbox_settings row with the matching account and enabled=1 in the test database only. Do not migrate synthetic grants or records to production.

## Operator-driven test checkout
In the Razorpay Test dashboard create an INR monthly or yearly plan and a single-quantity subscription with no trial, discount, addon, or plan change. Use finite billing cycles, expiry and clear test terms. Record the provider plan ID, actual amount in paise, interval and title in billing_plans. After checking exact plan and member identity, record the provider subscription ID, plan, immutable expected amount, test checkout short_url and expiry in billing_subscriptions. Never trust member-supplied subscription IDs, amounts or ownership. No API endpoint creates subscriptions; one test link per member is manually provisioned by operator. Members see their own test link and billing history on /account/membership. The cancellation form records a cycle-end cancellation request only. Operator must actually cancel in Razorpay and reconcile outcome before marking confirmed/rejected; no automatic cancellation, refund issuance or self-serve checkout creation in this phase. Do not tell customers that cancellation is complete based on a request.

## Webhook reconciliation
Configure Test Mode webhook at the confirmed member host /webhooks/razorpay-test. Use subscription lifecycle and refund events. The raw bytes are HMAC-SHA256 verified, account and event ID checked; only minimal event metadata and digest are stored. No email, contact, payment method or card data persisted. Unknown subscription mapping returns retryable error. Only subscription.charged with matching known plan, quantity, expected full amount, INR, invoice, positive paid_count and plausible cycle dates is eligible. Independently GET the payment with test keys to confirm capture, invoice and refund amount. Exact signed cycle boundaries determine access, not receipt time. An activation/authentication event alone grants nothing. Charge IDs, invoice IDs and subscription cycle numbers are unique; replay cannot extend expiry. A D1 transaction records the event, charge and entitlement. Refund created/processed events put payment on hold, including events delivered before the charge. Any observed refund amount blocks automatic entitlement; failed refunds and partial refunds need human review, no automatic regrant. Cancellation/failed renewals do not fabricate future entitlements; existing paid periods run until expiry or refund hold. Status history displays latest recorded event, not a reconciled live provider state.

## Production gates
This is deliberately limited: verify real Test Mode payloads (initial charge, renewal, pending/halted, cycle boundaries and partial/full refund), mapping, provider API responses and D1 transaction behavior. Unexpected payment/plan mismatch, duplicate invoices/cycles, retry ambiguity, webhook secret rotation, missing webhook recovery, dispute handling, scheduled reconciliation, provider state, tax invoices, production billing policy, cancellation/refund SLAs, customer notification, merchant onboarding and recurring-mandate compliance need explicit production work. Do not enable real charges, publish prices or represent the test cancellation interface as a production facility. Automatic checkout creation, actual cancellation API, institutional membership, pricing and billing terms remain unimplemented. Tests use synthetic payment API responses and SQLite D1 test double; no real provider request has been made.
